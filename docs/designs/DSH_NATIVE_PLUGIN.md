# Design: dsh-gbrain — gbrain as a native DeepSeek Harness coding plugin

Generated by /office-hours on 2026-10-08
Branch: master
Repo: Drachemann/dsh-gbrain (fork of garrytan/gbrain)
Status: APPROVED
Mode: Builder, with a public-audience constraint carried in
Supersedes: nothing. First design on this branch.

## Problem Statement

`dsh-gbrain` is a fork of gbrain, the code-intelligence and memory brain. Today it is
upstream gbrain with nothing added: `master` and `upstream/master` are the same commit
(`5b5891069`, v0.60.102.0). The task is to make gbrain usable natively from a DeepSeek
Harness session as a first-class plugin, focused on coding, tightly integrated with
dsh-gstack, while keeping upstream merges cheap enough to actually do.

gbrain already integrates with several hosts: an OpenClaw context-engine plugin, a Claude
Code plugin tree, a Codex plugin tree, and a `gbrain-coding` persona variant. So "add a
host" is a rung gbrain has climbed before. The interesting problem is not whether a DSH row
can exist; it is which row, where it runs, and how much of the fork it costs.

"General agent memory" goes to a separate fork of dsh-memory-evolve, which will consume
gbrain as a backend where that makes sense. `dsh-gbrain` therefore owns coding memory and
code intelligence; the other plugin owns everything else. gbrain's general memory surface
stays available for coding-relevant memory.

## What Makes This Cool

The thing you cannot do today: ask "who calls `performSync`" and get an answer, from the
session you are already in, with no API key and no per-query process spawn.

gbrain's code graph is built entirely locally — tree-sitter WASM chunking, edge
extraction, an in-file symbol resolver, two edge tables. No LLM touches it. Everything
that makes `code_def`, `code_refs`, `code_callers`, `code_callees`, `code_blast` and
`code_flow` work is free, offline and deterministic. A coding agent with a warm Postgres
brain behind a typed tool gets call-graph answers that grep structurally cannot give, at
zero marginal cost.

The second cool thing is the shape of the seam. dsh-gstack's rendered skills already
contain `gbrain` calls in prose, guarded by "skip if `gbrain` is not on PATH". A working
`gbrain` binary plus a tool surface means the preamble blocks that were written and never
activated light up for free.

## Constraints

1. **DSH runs under Node, and gbrain's TypeScript will not load there.** Verified: `dsh`'s
   shim ends in `exec node .../dsh/lib/bin.js`, and `bin.js` is `#!/usr/bin/env node`.
   Probing `node --input-type=module -e "await import('gbrain/engine-factory')"` fails with
   `ERR_UNSUPPORTED_TYPESCRIPT_SYNTAX: TypeScript parameter property is not supported in
   strip-only mode`. Same failure for `gbrain/operations`. 72 parameter properties across
   65 `src/` files, plus `with { type: 'file' }` imports (Bun-only, 11 modules) and 61 MB
   of committed tree-sitter WASM under `src/assets/wasm/`.
2. **The six code-intelligence reads refuse non-trusted callers.**
   `src/core/ops/code-intel.ts` wraps that read set so a caller whose `ctx.remote !== false`
   gets a refusal naming upstream issue #5052, pinned by
   `test/code-intel-remote-suspension-message.test.ts`. The stdio MCP server dispatches
   `remote: true`. **MCP cannot serve the code graph at all today, on any surface,
   including a local pipe.** `--surface verbs` (the surface gbrain's own docs recommend for
   coding agents) contains no code operations whatsoever.

   **What the suspension is actually for.** Not "agents must not read code". The source
   comment at the wrapper states it: *"Raw code fragments and cached traversals do not yet
   support the complete remote read policy."* The refusal text says the reads "stay
   suspended until they support the remote read policy", names `garrytan/gbrain#5052` as the
   follow-up, keeps `search` and `query` open, and — crucially — **names the supported lane:
   the trusted local CLI on the brain host**, via `gbrain call <op> '<params_json>'`. The
   control is about a *remote* read policy: network transports, the OAuth surface, per-client
   grants and source scoping over an untrusted transport. It is not a prohibition on an
   agent reaching a code graph, and gbrain itself ships the lane that does.

   **Why this plugin does not bypass it.** The helper *is* the trusted local lane the
   refusal recommends, with better ergonomics than a `gbrain call` spawn per query. It
   holds `ctx.remote === false` everywhere, so it does not weaken the control; and because
   that posture means gbrain's own remote scoping never runs, this plugin **adds the
   equivalent guard one layer up** in the Routing and Trust Contract: a per-session allowed
   source set, uid-checked socket, `0600`, and a refusal that names the source. The
   suspension's own failure mode — an agent reaching raw code fragments and cached
   traversals without the remote read policy applied — is the failure mode we re-implement
   the protection against. Read together with this section, Success Criterion 2 is a claim
   with a stated rationale rather than an unexplained bypass.
3. **One MCP mount can only see one source.** Recorded in the `dsh-gstack` checkout as TODO
   MEM-3: the grant binds to the cwd repo's code source, so a memory write is refused, and
   re-pointing the mount trades away code reads. Per-call routing needs a long-lived
   engine, not a mount.
4. **Upstream is a fast-moving, opinionated codebase.** The `/ship` skill, a five-file
   version lockstep, a mandatory 4-segment version, 13 generated artifacts guarded by
   `--check` scripts, module-size and function-size ratchets, an engine-SQL ratchet, and a
   rule that engine-live code must not use runtime dynamic `import()`.
5. **The free tests must stay green.** The full list is stated once, in Gates below, and
   referenced everywhere else rather than restated.

## Premises

Confirmed with the user, with two corrections.

- **P1 (restated after review).** The native surface is **two rows of a single bundle**: a
  **Host row** that publishes the engine service and the backend contract and registers no
  tool, plus a **preset row** that carries the tool declarations. The original P1 said the
  Host row carried "a service plus a tool surface"; that contradicted the placement
  decision and the `dsh-wyrmbrain` precedent it cites, so it is corrected here. The reason
  for a Host row at all is that one MCP mount cannot route between a code source and a
  memory source, and because **six** code operations refuse remote callers outright — the
  six are `code_callers`, `code_callees`, `code_def`, `code_refs`, `code_blast` and
  `code_flow`, derived from `src/core/ops/code-intel.ts`, where the read operations are
  wrapped as one set and pinned by `test/code-intel-remote-suspension-message.test.ts`. Any
  count of that set elsewhere in this document means those six.
- **P2 (corrected by the user).** `dsh-gbrain` focuses on coding. General memory is a
  separate fork of dsh-memory-evolve, which either consumes gbrain-derived functions as a
  backend or has its features integrated into gbrain; the user's own reasoning is that
  making dsh-memory-evolve *depend on* gbrain is the option that keeps upstream merges
  tractable, and that merging dsh-memory-evolve's features into gbrain would make upstream
  merges hard. gbrain's general memory surface remains available for coding memory.
- **P3.** Upstream keeps arriving as ordinary `git merge`s on `master`. Merge cost is
  contained by keeping the fork additive: apart from a new fork-owned CI workflow and two
  marked insertions into `AGENTS.md`, **the fork edits no upstream-owned file at all.** In
  particular it does not touch `package.json` for versioning. Upstream rewrites the version
  stamp on every release, so a fork that bumped it would manufacture a conflict in a file
  upstream changes constantly; instead the fork tracks upstream's version and records its
  own plugin version in `dsh/package.json`, which upstream will never touch. The recurring
  cost is the opposite of a conflict: after a merge, `bun install` refreshes the lockfile
  and the fork's running version is whatever upstream said it was.
- **P4.** The `gbrain` CLI stays working under that name and its documented flags, so the
  eleven rendered dsh-gstack skills that call it keep degrading correctly today and
  activate for free once a brain exists.

## Approved Decisions

| # | Decision | Chosen |
|---|---|---|
| D1 | Session mode | Builder, public-audience constraint carried in |
| D2 | Native shape | Host row holding a warm engine, routing per call, publishing a backend for dsh-memory-evolve |
| D3 | Brain engine | Postgres + pgvector in podman. PGLite out of scope entirely |
| D4 | Runtime host | Resident Bun helper owning the engine connection; DSH talks NDJSON over a Unix socket |

**MEM-3 had two limbs, and different decisions remove each.** Constraint 3 records it as one
problem; it is two. Limb (a) is **engine process exclusivity**: PGLite is openable by one
process at a time, so a second reader could not simply open the same brain. Limb (b) is
**the mount's single-source grant**: the MCP server dsh spawned bound its write grant to the
cwd repo's code source, so a memory write was refused and re-pointing the mount traded away
code reads. **D3 removes limb (a)** — a Postgres brain in a container has no
process-exclusivity constraint, so the plugin stops being the database's owner and becomes a
client. **The Host row plus per-call routing removes limb (b)** — routing is resolved per
call rather than fixed at mount time, and the Routing and Trust Contract states the allowed
set. Neither decision alone is sufficient, which is why both P1 and D3 are load-bearing.

The consequence is worth stating plainly: the plugin, the `gbrain` CLI, a cron job and a
background indexer all connect concurrently, and each routes per call with its own
`source_id`.

## The Chosen Shape

One shape, stated once, so nothing below contradicts it.

> A **Host row** in the DSH composition supervises a **resident Bun helper** that holds one
> connection to the Postgres brain. The helper answers newline-delimited JSON requests over
> a Unix socket. A **preset row** declares fourteen tools whose handlers call that socket.
> The Host row publishes `gbrainBrain` (the request surface) and `gbrainBackend` (the
> narrow contract dsh-memory-evolve will consume). The Host row registers no tool.

**Why a helper rather than a transpiled import.** A transpiled tree would work. It would
also couple the plugin to gbrain's *internal module paths* — `src/core/ops/code-intel.ts`,
`src/core/code-intel/recursive-walk.ts` and their neighbours — which upstream may
reorganise without notice and with no obligation to us. The helper couples us to gbrain's
*exported subpaths* instead: `./engine-factory`, `./operations`, `./config`. That is the
difference between a merge we do and a merge we fight. The CLI is deliberately **not** the
boundary, because a long-lived engine connection with per-call routing cannot be expressed
as one CLI invocation per call without paying gbrain's startup cost every time; the CLI
stays supported for P4 and for everything outside this plugin.

**Why a preset row for the tools, and what generates it.** A preset declaration carries
its complete plugin list and has no `extends`, so a preset that adds tools must copy the
shipped list. `dsh-wyrmbrain` does exactly this, and its comment explains why the copy must
be generated rather than hand-maintained: overriding `preset-standard` instead *"would
silently drop every tool a future DSH adds."*

Two different things are generated, and conflating them was a review finding. `lib/tools.js`
is the single source of truth for **our fourteen tools**, and from it `gen-surface.mjs`
writes the manifest, the tool half of the README, and the tool rows of both patch files.
The **copied DSH plugin list** is a separate input: it is read at generation time from the
installed shipped preset, whose declaration row the preset patch extends, in the profile's
`node_modules/@deepseek-ai/dsh-agent-preset/skills/.../` tree. `gen-surface.mjs` locates
that file, composes the copy from it, and `--check` re-reads it and fails when DSH has
shipped a plugin the copy does not carry. That is what makes the wyrmbrain failure mode
impossible instead of merely documented.

The preset declaration row this patch extends is named once, concretely: it is the same row
dsh-gstack's own generated preset already carries in this profile, `preset-dsh-drache-technik`
(`config.id: dsh-drache-technik`) in `dsh-gstack/.dsh/agent-modes/dsh-drache-technik/cordis.patch.yml`.
Our `presets/gbrain-tools.patch.tmpl.yml` carries the same `id` and the same `config.id`,
so it is an **override of that row**, not a second preset. Overriding by row id replaces the
complete `config`, so the template restates `id`, `plugins` and every other field — which is
exactly why the copy must be generated.

**What we deliberately do not do.** We keep the `gbrain` binary working (P4) and we do not
move dsh-gstack's skill prose from CLI calls to typed tools. Those eleven rendered skills
work today and cost nothing to keep working. Migrating them is a separate, later, optional
change in the other repository.

## Routing and Trust Contract

Per-call routing is the reason this plugin exists, so it is specified rather than assumed.

**How the Host row learns the project root.** Everything below depends on it, and the
harness process cwd is `~/.dsh`, not the session project — so cwd is wrong by default and
using it would resolve both routing tiers against the wrong directory, failing in a way that
looks like an empty brain rather than a bug.

The root arrives through the **tool execution context**, and this is the field R2-12 asked
to be named:

| Value | Path | Reached from |
|---|---|---|
| project root | `exec.agent.session.header.cwd` | the tool's `execute(args, exec)` second parameter |
| session id | `exec.agent.id` | the same object |

Verified against the installed runtime, not recalled: `dsh-tool-bash` reads exactly
`exec.agent?.session.header.cwd ?? process.cwd()` and declares **no `inject` at all**.

**There is no Cordis service named `session`.** `ctx.sessions` is a *registry*
(`create`/`get`/`list`), not the current session. Cordis's rule — recovered from the
installed runtime — is that reading an undeclared property throws
`cannot get property "<name>" without inject`; it throws because the key is absent from
`ctx.reflect.props`, which is the case for `session`. A row that reads `ctx.session` gets
that throw on every call.

The root is therefore a property of the **call**, not of the plugin: `apply()` runs once per
process while routing runs once per request, so a root captured at activation could never be
the caller's project. The Host row resolves it per request and never reads it off `ctx`.

A session with no project root — a headless run, or a session started outside a
repository — resolves a **`null`** root (never `undefined`, and never a fall back to a
config default) and every brain op fails with `no_source_for_project`, whose fix text names
`gbrain sources add`. That failure is the designed outcome, not a fallback: silently
querying `default` is how one project reads another's code. The refusal is issued **before**
the source registry is loaded, because the registry load dials the helper and a refusal that
dials first is not a guard.

> **This paragraph is a correction, not a description.** Until 2026-10-11 the row read
> `ctx.session.dir` and `ctx.session.id`. Both threw, so all fourteen tools were dead and
> the failure named no row. Three guards each missed it: the inject scan in
> `dsh/test/preset.test.js` read two of the three files that touch `ctx` (and read comments
> as code), `fakeCtx` in `dsh/test/host-entry.test.js` supplied `ctx.session` itself, and
> this section named "the session record" without naming a field. See the regression tests
> `exec: the session root is read from exec.agent.session.header.cwd` and its two siblings.


**Where `source_id` comes from.** Not from the model. A tool handler never accepts a
`source_id` parameter. The Host row resolves it per session, in this order:

1. The session project root's `.gbrain-source` dotfile, when the file exists and names a
   source the brain knows. This is gbrain's own per-repo routing tier, reused rather than
   reinvented.
2. Otherwise the source registered against that project path, resolved once at session
   start by the helper and cached for the session.
3. Otherwise the call fails with `no_source_for_project` and the fix text names
   `gbrain sources add`. It does not silently fall back to `default`. gbrain's own dispatch
   layer refuses an unscoped remote call for the same reason
   (`missing_source_scope`), and we keep that posture.

**The allowed set.** The Host row resolves, once per session, the set of sources that
session may address: the project's own source, plus the memory source named in the plugin
config (`memorySourceId`), and nothing else. A request naming a source outside that set is
refused with `source_not_allowed` and the refusal is logged. Reading another project's code
this way is a data-leak class, and gbrain's `sourceScopeOpts` exists to prevent it; because
we call gbrain as a trusted local caller, that machinery is bypassed by construction, so we
reimplement the same guard one layer up in the Host row. This is a deliberate duplication
of a check, and it is the one place where duplicating is safer than delegating.

**Who may reach the socket.** The socket lives at
`$XDG_RUNTIME_DIR/dsh-gbrain/<database-fingerprint>.sock`, or `~/.dsh/gbrain/` when
`XDG_RUNTIME_DIR` is unset, mode `0600` inside a `0700` directory. The socket
is keyed by a fingerprint of the `database_url` (a truncated SHA-256), so a second
profile pointing at a different database gets its own helper rather than silently querying
the first profile's brain. A second profile pointing at the *same* database reuses the
helper, which is correct because the database is shared state.

*Corrected 2026-10-11.* This section previously also claimed the helper "verifies the
connecting peer's uid with `SO_PEERCRED` / `LOCAL_PEERCRED` and refuses a mismatch".
**No such code was ever written**, and the claim has been removed rather than left as an
implemented control. It is not needed: on Linux an `AF_UNIX` filesystem socket cannot be
opened by a uid other than the one holding write permission on it, so the `0600` mode
inside a `0700` directory **is** the enforcement, applied by the kernel. What the helper
does verify, in place of a peer-uid check, is that a socket file it finds was not left by
a *live* helper: it reads `owner.json`, probes the pid, and refuses with exit 3 rather than
stealing a socket a running process is using. That check is pinned by
`dsh/test/engine-host.test.js`.

**The trust claim, made testable.** Success Criterion 2 is not an assertion, and it does
**not** rest on a uid check — it rests on the file mode. Two tests carry it: (a) the socket
is created `0600` in a `0700` directory and a socket owned by a live pid is refused rather
than taken over, and (b) a request naming a source outside the session's allowed set is
refused. The plugin adds no path for a *remote* caller to reach a code read, because every
call is a local trusted call made on behalf of the session that owns the socket, and the
socket's access is kernel-enforced by its mode.

## The Wire Contract

`dsh/lib/protocol.js` is written first, before any tool, and both sides import it.

- **Framing, and who measures size.** Newline-delimited JSON, UTF-8, one object per line.
  The **request** limit is 1 MiB and the **client** refuses an oversized request before it
  is written. The **response** limit is 1 MiB and the **helper** measures it: it serialises
  the result, and if the line would exceed the limit it discards the result and substitutes
  a bounded `payload_too_large` error carrying that request id. `code_blast` and `code_flow`
  are the two ops most likely to trip this, which is why they also get the longest
  deadlines. The refusal is itself size-bounded, so it can always be delivered. A client
  that reads an over-limit line anyway — only possible from a helper that is not ours —
  drops the connection and fails every in-flight request with the same code.
- **Version handshake.** The first line the helper writes on connect is
  `{"v":1,"hello":"gbrain-helper","build":<monotonic build id>,"schema":<database schema version>,"db":<full database fingerprint>}`.
  `v` is the **wire protocol** version. `build` is a monotonic integer the plugin increments
  whenever the helper's behaviour changes, which is what makes a stale helper detectable at
  all: this fork's own versions are `0.x`, so a semantic version could never produce a
  mismatch. `schema` is gbrain's **database** schema version, not the wire version, and is
  named here so its owner is not ambiguous.
  The rule is stated once, positively: **the client may connect to any helper on that
  socket and read its hello; it sends requests only when `v`, `build` and `db` all match its
  own, and otherwise stops the helper by the pid in `owner.json` and starts a fresh one.**
  `db` must be the full fingerprint, because reuse across profiles is correct only when the
  database is genuinely the same one. A mismatch of any of the three is fatal to the
  session, not negotiated.
- **Request.** `{"id":<int>,"op":<string>,"params":{...},"source_id":<string|null>,"deadline_ms":<int>}`.
  `id` is monotonic per connection and is echoed. `deadline_ms` is a **relative** budget
  measured from the helper's receipt of the line, not an absolute timestamp, so a clock
  difference between the two processes cannot shorten or extend it; it is on the wire rather
  than client-local so that two conforming implementations cannot disagree. `source_id` is
  `null` for the two **control ops** — `probe` (liveness and engine status, used by the
  health check) and `shutdown` (graceful stop, used by `dispose`) — and required for all
  fourteen brain ops. Those two are the only ops with `source_id: null`, and they are named
  here so an implementer can tell which requests are rejected.
- **Response.** `{"id":<int>,"ok":true,"result":<object>}` or
  `{"id":<int>,"ok":false,"error":{"code":<string>,"message":<string>,"why":<string>,"fix":<object>}}`.
  The error envelope is gbrain's own `code` / `why` / `fix.next` shape, passed through
  rather than flattened.
- **Timeouts and cancellation.** `deadline_ms` defaults are the client's: 15,000 for a read,
  120,000 for a write, and 180,000 for `code_blast` and `code_flow` because they walk a
  graph. The helper enforces the deadline it was sent; on expiry it answers
  `deadline_exceeded` for that id if the operation can be abandoned, and otherwise the
  client drops the connection and treats it as unhealthy. There is no in-flight
  cancellation in v1; the client documents that a cancelled tool call may still complete
  server-side.
- **Concurrency.** Requests are multiplexed in flight. The helper executes reads
  concurrently against the Postgres pool and serialises writes through a single queue, so
  two `put_page` calls for one slug cannot interleave.
- **Restart behaviour.** While the helper is restarting, requests are queued with the same
  deadline. If the deadline expires first, the caller gets `helper_unavailable` with the
  restart count in `why`. A helper that fails three restarts in sixty seconds stops being
  restarted and the service reports degraded rather than flapping.
- **Lifecycle.** The Host row starts the helper on activation and stops it on `dispose`,
  which covers plugin upgrade and `remove_bundle`. A stale socket file whose owner is gone
  is unlinked on startup after a connect probe confirms nobody is listening; a helper that
  outlives its plugin is detected by the version handshake and stopped by pid, recorded in
  the socket directory's `owner.json`.

Every clause above gets a test in `dsh/test/protocol.test.js`. A clause with no test is not
part of the contract.

## The Operation Surface

`dsh-gbrain` owns coding; general agent memory belongs to the dsh-memory-evolve fork, which
reaches this brain through the backend contract rather than through these tools. Exactly
**fourteen** tools, and `dsh/lib/tools.js` is the single source of truth for that list. The
manifest, both patch files and the README are **generated from it** by
`dsh/scripts/gen-surface.mjs`, and `gen-surface.mjs --check` fails when any of them
disagrees. The prose below is a description of that file, not a second list.

| Group | Tools | Why |
|---|---|---|
| Code graph | `code_def`, `code_refs`, `code_callers`, `code_callees`, `code_blast`, `code_flow` | The reason this plugin exists. All six are refused to MCP callers, so they are reachable only through this row. |
| Code-aware retrieval | `query` | The superset of `search`; carries `--lang`, `--symbol-kind`, `near_symbol` and `walk_depth` for two-pass structural expansion. `search` is not exposed because `query` covers it. |
| Page reads and writes | `get_page`, `put_page` | What dsh-gstack's save blocks need, with routing resolved by the Host row. |
| Coding memory verbs | `recall`, `remember`, `context_pack`, `forget`, `delta` | Five of gbrain's frozen seven-verb surface: what a coding turn needs to carry a decision forward, budget the context pack, withdraw a fact when code changes, and ask what changed since a marker. `entity` and `synthesize` stay with the memory plugin, which owns the graph of people and companies. |

Not exposed, and deliberately: the chronicle, ontology, takes/think/calibration, facts
extraction, salience and insight reads, transcripts and connectors, Google and open-loops,
reports and ops, skillpacks and brain membership, decide/TypeSafe, autopilot and minions,
mounts and federation, files and raw data, eval, schema packs, and the admin surface.
`reindex-code` is **not** a tool — it is a long-running, potentially expensive operation
that belongs to an explicit operator command, not to a model that might call it twice.

One correction to a number that circulated during this session: the recursive traversal
operations `code_blast` and `code_flow` support **four** languages —
`['typescript', 'tsx', 'javascript', 'python']` — not the 36 the chunker can parse.
Verified at `src/core/code-intel/recursive-walk.ts:65`. The non-recursive reads and the
symbol columns are language-agnostic. This is upstream's limitation, and it belongs in the
README so nobody promises a universal call graph.

**How a degraded result reaches the model.** gbrain's agent contract is not flattened into a
generic error. `dsh/lib/result.js` maps it for every tool:

- A normal result renders as compact text plus the structured value, so the model sees both
  the answer and the machine-readable envelope.
- `code` / `why` / `fix.next` are preserved verbatim. `fix.next: "run"` and `"wait"` render
  the exact command or delay; `"tell_user_to_run"` and `"ask_user"` surface as a blocked
  result with the user-facing message intact, and the tool result says plainly that it needs
  the user. gbrain's exit code 3 means "stop and ask the user", and a tool result that
  swallows it would be the most likely first user-visible failure of this plugin.
- `[gbrain notice …]` and `[AGENT]` blocks pass through as their own rendered text, never
  stripped, so "a degraded result is not proof of no notes" survives the adapter.

**Search mode and the keyless claim.** Three exposed tools — `query`, `recall`, `remember` —
depend on the brain's search mode and, for semantic search, an embedding provider. The code
graph does not, and that distinction is the pitch: the six code tools are free, offline and
keyless; the retrieval and memory tools are only as good as the brain's configured mode.
The install flow therefore **stops and asks**, relaying gbrain's own cost matrix rather than
accepting a default, exactly as gbrain's install protocol requires. The README states the
same matrix and what each of the three tools does in `--no-embedding` mode: keyword search
only, with symbol and language filters still working because `symbol_name_qualified` is
weighted 'A' in the chunk tsvector.

## Index Freshness

The graph answers "who calls `performSync`" correctly only if it was built after the code
changed, so freshness is part of the contract rather than an operational afterthought.

- **Who indexes, and when.** Two paths. (1) At session start the Host row asks the helper
  for the project source's indexed revision and compares it to git HEAD; a mismatch is a
  *stale* signal, not an automatic re-index. (2) The operator runs
  `gbrain sync --source <id>` — the explicit command, named in the README — or
  `gbrain reindex-code --source <id>` for a full backfill after a `CHUNKER_VERSION` bump or
  a merge. **The plugin never syncs on its own initiative in this wave:** a background write
  storm triggered by a session is exactly the surprise the exclusion of `reindex-code` as a
  tool was meant to prevent.
- **Staleness reaches the model.** Every code-tool result carries `indexed_at` and
  `possibly_stale` (true when the source's indexed revision differs from the working tree's
  HEAD at call time). The rendered text leads with the answer and appends a one-line warning
  only when `possibly_stale` is true, so a stale graph never masquerades as an empty one.
  gbrain already has the vocabulary for this — its readiness contract returns
  `not_built` / `no_symbols` / `indexing` / `ready` — and we surface its `status` rather than
  inventing a second one.
- **The test that carries it.** A synthetic source whose HEAD moves after indexing must
  produce `possibly_stale: true` on a subsequent code read, and a source never indexed must
  produce gbrain's own `not_built` readiness rather than an empty result.

## Write Policy

Two tools write: `put_page` and `remember`. Both are subject to the same rules.

- **Target.** Routing is resolved by the Host row, never by the model. A write lands in the
  session's `memorySourceId` when the plugin config names one, and otherwise in the
  project's own source. It never lands in a code mirror by accident, which is the MEM-3
  failure this replaces.
- **Provenance.** Every write is stamped with the session id, the project path, the plugin
  version and the tool name, so a misrouted page can be found later.
- **Consent.** A model-initiated write is a normal tool call, and the harness's own
  approval policy governs it; there is no second confirmation layer invented here. What the
  plugin does guarantee is that a write is never silent: every write returns the resulting
  slug, the source it landed in, and whether it created or updated, so the transcript shows
  where it went.
- **Reversal, split by surface.** For a remembered fact, `forget` is one of the fourteen
  tools, so the model has a session-available withdrawal path and the README says so. For a
  page, `get_versions` and `revert_version` are **operator-only in this wave** — they are not
  tools, and the README gives the two commands. That is the right authority split: a model
  may withdraw a fact it wrote this session, and an operator decides when to roll a page
  back.

## Logging

`dsh/lib/log.js` writes to `~/.dsh/gbrain/logs/helper-<fingerprint>.jsonl`, mode `0600`
in a `0700` directory, one JSON object per line, ring-rotated at 5 files of 5 MiB. Levels:
`error` always, `warn` always, `info` for lifecycle and every request's op, source, outcome
and duration. **Payloads are never logged.** Request parameters and results are redacted to
their shape: a `put_page` or `remember` call logs the slug and the byte count, never the
content. Success Criterion 1's traceability reads this file, and the test that proves
payloads are absent is part of the logging contract.

## The Backend Contract

`dsh/lib/backend-contract.js` exists because the user asked for it, and review was right
that it cannot be specified against a consumer that does not exist yet. It is therefore
**descoped to a versioned stub with a stated first negotiation**, not a designed interface:

- The file exports `BACKEND_VERSION = 1` and a single async
  `negotiate({ wants })` returning a capabilities object. Today it returns
  `{ version: 1, operations: ['recall','remember','forget','context_pack','delta','get_page','put_page'], writes: 'caller' }` and nothing else.
- **Write ownership is stated, not delegated:** the caller owns what it writes; the backend
  never synthesises content on the caller's behalf.
- The full request/response shapes are **not** designed here. They get designed in the
  session that builds the dsh-memory-evolve fork, against a real consumer, and this
  document is not a substitute for that.
- The test that would fail if the contract broke is
  `dsh/test/backend-contract.test.js`: it asserts the version field, the operation list, and
  that a consumer asking for an unknown operation gets a named refusal rather than
  `undefined`.

## The Advisory Seam: Descoped, then RESOLVED (2026-10-11)

Review was right: building a typed `planAdvisory` seam and an `external` advisory kind for

**Which repository gates inspect `dsh/`.** None of gbrain's own, by construction:
`scripts/run-unit-shard.sh` discovers `test/**/*.test.ts` and the module-size and coverage

## Distribution Plan

The deliverable is a git repository plus a DSH bundle inside it.

```bash
git clone <fork-url> <repo>
cd <repo> && bun install
bun link                                  # puts the FORK's gbrain on PATH, not upstream's

# pgvector, loopback only, persistent, password kept out of the shell history
umask 077
printf 'POSTGRES_PASSWORD=%s\n' "$(openssl rand -hex 16)" > ~/.gbrain-pg.env
podman volume create gbrain-pgdata
podman run -d --name gbrain-postgres --restart unless-stopped \
  -p 127.0.0.1:5432:5432 --env-file ~/.gbrain-pg.env \
  -v gbrain-pgdata:/var/lib/postgresql/data pgvector/pgvector:pg16

# one connection URL, exported, then used everywhere
export GBRAIN_DATABASE_URL="postgresql://postgres:$(cut -d= -f2 ~/.gbrain-pg.env)@127.0.0.1:5432/gbrain"
gbrain init --url "$GBRAIN_DATABASE_URL"   # STOP here and choose a search mode
gbrain sources add dsh-gbrain --path <repo>
gbrain sync --source dsh-gbrain
```

Then, in DSH, using the `link:` spec form this family already uses (dsh-gstack is installed
as `link:<dsh-gstack-checkout>/.dsh/plugin`):

```
plugin_manager { action: "install_bundle", target: "link:<repo>/dsh" }
```

**Then configure the row, which is a real step and not optional.** The bundle deliberately
ships no `database_url`, following dsh-gstack's `stateDir` precedent: the harness process
cwd is `~/.dsh`, so a per-deployment value must come from the profile, not from the
package. The profile patch supplies:

```yaml
- id: gbrain
  name: dsh-gbrain
  config:
    databaseUrl: ${GBRAIN_DATABASE_URL}
    memorySourceId: gstack-brain-matt
    # codeTools: true          # see Open Question 7
```

**When `databaseUrl` is unset.** The Host row does not fail activation, because activation
failure is measured by gbrain's own install ladder — *"Ladder-driven (harness installs) —
`gbrain init --prefer-postgres` probes …"* — and a brain-less profile must still be usable.
Instead the row activates, publishes `gbrainBrain` in a **degraded** state that reports a
named reason, and every brain tool call fails with `brain_not_configured` whose fix text
names both remedies: set `config.databaseUrl` in the profile patch, or export
`GBRAIN_DATABASE_URL`. Resolution order is config, then `GBRAIN_DATABASE_URL`. This mirrors
gbrain's own posture for a missing database and is the same shape as the routing contract's
explicit `no_source_for_project` refusal for a missing source: a named absence, never a
silent default. A test asserts that an unconfigured row activates and that its first brain
tool call returns `brain_not_configured` naming both remedies.

The volume, the restart policy, the `0700` umask and the exported URL are all load-bearing:
without the volume, the "single source of truth" is destroyed with the container, and
without the export, `gbrain init --url` gets an empty string.

There is no build step for the plugin itself — plain JavaScript plus one generator script,
matching both `dsh-gstack` and `dsh-wyrmbrain`. `bun link` is named explicitly because
`gbrain` is already a public package name and a bare `gbrain` on PATH may be an upstream
build from a different commit; P4 depends on the fork's build being the one that answers.
Publishing to npm is out of scope for this design.

## Open Questions

1. **Does the helper actually serve a code read?** Not yet verified end to end, because
   `node_modules` is empty in the fork (`ls -A node_modules | wc -l` → 0) and nothing can
   run until `bun install`. The refusal path is verified in source; the success path is
   not. This is Next Step 1 and the single highest-value hour in the plan.
2. **Does `gbrain` self-reference resolve from inside `dsh/`?** The exports map covers the
   subpaths we need and Node honours `exports` for self-references, but this has not been
   executed. Fallback is a relative import to `../src/`, which is uglier but certain.
3. **Is the Bun startup cost acceptable per helper start?** A resident helper pays it once
   per session; a cold start pays it per request. Not measured.
4. **How does the Host row receive `database_url`?** `dsh-gstack`'s bundle deliberately
   leaves `stateDir` unset because the harness process cwd is `~/.dsh`, not the session
   project, and supplies it from the profile patch. Ours should follow the same pattern,
   which means the profile-side value in the Distribution Plan and the per-database socket
   key in the Routing and Trust Contract. Multi-profile behaviour is specified there; the
   config plumbing is not yet written.
5. **Should the six code tools be opt-in?** The suspension in Constraint 2 is upstream's
   remote read policy, and this plugin re-implements the equivalent guard locally. An
   explicit `config.codeTools` flag defaulting to *on* would make an operator's consent
   recordable rather than implicit, and is cheap. It is listed here rather than designed
   because the right default depends on whether this is published, which is Open Question 6.
6. **Does a fourth agent type need a narrower surface?** The fourteen tools are declared for
   every session in the profile. If a subagent or a workflow lane should not reach
   `put_page`, that is a preset-scoping decision to make once, in the preset row, when a
   real case appears. Not designed now.
7. **Distribution and naming.** The user intends to publish to GitHub for others. That means
   a name the fork does not already shadow, a README that says what upstream does not, the
   `LLMS_REPO_BASE` regeneration gbrain's own fork note mandates, and a decision about
   whether a stranger installs a container before their first query.

Constraint 3 records it as an MCP-mount limitation (the grant binds to the cwd repo's code source, so a memory write is refused, and re-pointing the mount trades away code reads), while the D3 paragraph says PGLite being openable by one process at a time is the entire reason MEM-3 had to choose between memory writes and code reads. D3 removes only the second cause and the Host row only the first, so a reader cannot tell which decision actually fixes MEM-3.

**Remedy**

> Attribute MEM-3 to both limbs explicitly (engine process exclusivity and the mount's single-source grant) and say which decision - D3, D4 or the Host row - removes each.

### R2-7 — consistency

**Problem**

> Layout says package.json gets the upstream version bump which upstream rewrites on every release anyway, and Success Criterion 4 counts an auto-rewritten version stamp as new upstream-owned-file content, but no mechanism is named for that rewrite and the design never says whether the fork edits an upstream-owned file that upstream changes on every release. If it does, the Criterion 5 promise of a conflict-free git merge upstream/master is at risk on exactly that file.

**Remedy**

> State whether the fork edits package.json at all, name what rewrites the stamp on merge if it does, and either drop the bump or record the recurring package.json resolution as an accepted merge cost in Criterion 5.

### R2-8 — consistency

**Problem**

> The Request schema is fixed as id, op, params and source_id and the Response schema as id, ok, result or id, ok, error, but Timeouts and cancellation says each request carries a deadline, with 15 s and 120 s client defaults and a longer deadline for code_blast and code_flow. The shapes the document declares cannot carry that field, so two conforming implementations would disagree about whether the deadline is on the wire or client-local.

**Remedy**

> Add the deadline to the request shape (for example deadline_ms, with absolute or relative semantics stated) and a test that an over-deadline request is answered with deadline_exceeded, or state that the deadline is client-local and the helper applies its own per-op cap.

### R2-9 — clarity

**Problem**

> The Request clause says source_id is required for every op that touches the brain and is rejected for the two ops that do not, but no op that does not touch the brain is ever named: all fourteen tools reach the brain and the lifecycle uses a connect probe and a pid stop rather than requests. The schema also types source_id unconditionally, so an implementer cannot tell which requests are rejected.

**Remedy**

> Name the two control ops and give them a shape (this is also where the connect probe and owner.json interlock), or delete the clause and require source_id on every request.

### R2-10 — clarity

**Problem**

> Framing says a request or response over 1 MiB is refused with payload_too_large rather than buffered unbounded, but says nothing about how a response is measured or refused. The helper must serialise before it can know a result's size - code_blast and code_flow, the two ops given the longest deadlines, are the likeliest to exceed it - and the client must read a line before it can reject it. What the caller sees when its own result is refused, and whether the refusal is itself size-bounded, is unspecified.

**Remedy**

> State who measures a response, that the helper substitutes a bounded payload_too_large error for that request id, and what the client does with an over-limit line from a helper (for example drop the connection and fail in-flight requests with the same code), with a protocol test.

### R2-11 — feasibility

**Problem**

> Stale-helper detection rests on the hello line {v, hello, plugin, schema}: the client refuses a major-version mismatch with helper_version_skew, which is also said to be how a stale helper left by an older plugin build is detected. Both version sources in this document are 0.x (upstream v0.60.102.0 per Constraint 4, protocol v = 1), so an older plugin build cannot produce a major mismatch, and the schema field's owner (wire protocol or database schema) is never stated. The same clause also says the client never talks to a helper it did not start except when the database fingerprint matches and the version does too - reading the hello is that conversation, and the exception's condition is the fact under test - and the hello carries no database fingerprint for the reuse rule to check.

**Remedy**

> Put a monotonic build or protocol id and the full database fingerprint in the hello, define which mismatch is fatal and what schema means, and rewrite the rule as: the client may connect and read the hello of any helper on that socket, but sends requests only when the build id and the database fingerprint match, otherwise it stops the helper by pid.

### R2-12 — completeness

**Problem**

> Routing tier 1 is the session project root's .gbrain-source dotfile, tier 2 is the source registered against that project path, and every write is stamped with the project path - but the document never says how the Host row learns the session project root, and Open Question 4 records that the harness process cwd is ~/.dsh, not the session project. A naive implementation resolves both routing tiers and the provenance stamp against the wrong directory, and the failure would look like an empty brain rather than a bug.

**Remedy**

> Name the DSH session field or session-start hook that supplies the project root, state its behaviour for a session with no project, and give the fallback failure (for example no_source_for_project) with a test.

### R2-13 — completeness

**Problem**

> Constraint 2 records that every code read refuses callers whose ctx.remote is not false (upstream issue #5052) and that MCP cannot serve the code graph on any surface, and the design deliberately makes those operations reachable to agent-facing sessions through a trusted local helper. The document never records what #5052 suspended those operations for, nor argues why a user-scoped socket answers that risk, so Success Criterion 2's claim that no new path exists for a remote caller cannot be evaluated and the plugin's value proposition rests on an unexplained bypass of an upstream control.

**Remedy**

> State the reason for the #5052 suspension (from the issue or the test that pins the message) and argue the threat model explicitly, or make the code tools an explicit opt-in that a profile must enable.

### R2-14 — completeness

**Problem**

> The Distribution Plan ends with plugin_manager install_bundle, while the Host row's database_url comes from a profile-side value (Open Question 4) and the flow only ever exports GBRAIN_DATABASE_URL in a shell. No step configures the plugin, and no behaviour is stated for a Host row whose database_url is unset - activation failure, environment fallback, or a degraded service - unlike the routing contract's explicit no_source_for_project refusal for the analogous missing source.

**Remedy**

> Add the profile-side configuration step to the Distribution Plan and specify the unset-database_url behaviour (a named activation failure or a documented GBRAIN_DATABASE_URL fallback) with a test.
